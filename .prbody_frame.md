The owner said on 2026-10-14 that the system must not need more memory than his 11,960 MB

holding three models at once, which no profile of this server can carry. This commit is the

Shape, and what was rejected

* One service, OFF by default, named `modelserver` in INSTALL_SERVICES. It is another entry in
  `brain.ops.overlays.OVERLAYS` (the mechanism the langfuse and presidio overlay introduced), so
  there is no second budget and no second settings mechanism: `plan`, `plan_in_room` and
  `memory_problem` cost it, the Settings save refuses a combination that does not fit, and the
  deploy hook starts it after each deploy. What this commit adds to the mechanism is a
  `Tuned` figure per overlay: the install chooses parts, an idle time and a memory figure, and the
  plan charges the limit those choices need rather than the component's fixed row.
* One part resident at a time, so the container's limit is the base plus the LARGEST part, not
  the sum. Rejected: the three models resident at once (item 120's 3,840 MB, which is why no
  server of his size could ever switch it on), and a container per part (three idle JVM and
  runtime floors for work that happens one document at a time).
* Idle ends the PART'S PROCESS, not the container. The supervisor runs each part as a child
  process and ends it after the idle time, so its memory goes back to the kernel. Rejected: the
  docker socket (a container with the daemon's socket is root on the host) and a host timer (a
  second thing to install on every server).
* Anonymous memory and memory-mapped weights are two figures and never their sum. The container
  limit covers both (a mapped file that does not fit is reclaimed under pressure, but the
  container still has to be allowed it); the host check counts only the non-reclaimable part
  against MemAvailable, which is the owner's "kernel cache counted" instruction read as
  arithmetic. No swap for the container (`memswap_limit` equals the limit), so a part that
  outgrows it is ended and reported rather than slowing the whole host.
* Smaller defaults than item 120. The default choice is the embedding part alone:
  Qwen3-Embedding-0.6B at Q8_0 (about 640 MiB of weights, memory-mapped) through llama.cpp,
  1,088 MiB container, 416 MiB of it non-reclaimable. Layout 1,344, scanned pages 576, general
  reader 832, entity finder 1,408. The default document ceiling is 25 MB (needs-rupash 119),
  and the container is sized for the ceiling of what the install admits.
* Every figure here is a judgement with a stated basis and `measured=False`, and the server
  reports its OWN peak per batch (anonymous and cache from its cgroup, split, never summed) so
  the settings screen can show a measured figure beside the judged one. The report is recorded by
  the product into `ops.model_server_peak`, a ring of 50 slots per part, never an invented
  number: a block that cannot be read is no report, and a bad figure is dropped without dropping
  the vector it rode with.
* When the host cannot hold the choice, the Settings save says so in words naming the part and
  the shortfall and refuses it, writing nothing; the same words are the deploy step's refusal
  and the install check's. A refusal is of this overlay only.

`src/inference_server/` is a separate stdlib program that imports nothing from `brain` (the two
are built and deployed apart); every spelling the two share (paths, report keys, part names,
environment variables) is held equal by a test reading both. Weights are fetched by a one-shot
container before the service starts and the weights volume is mounted read-only into it.
