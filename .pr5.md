What it adds, and why it is shaped this way

* The part answers the labels it was asked and no others, in the text's own offsets. Long text is
  read in overlapping windows (1,200 characters, 200 shared): the model reads a few hundred tokens
  and silently ignores the rest, which for a scrub is a clean first paragraph and an unscrubbed
  second. A span of a label nobody asked for, an empty or inverted one, one past the end and one
  under a floor score are dropped, never repaired: a span one character out is the half-redacted
  name the scrub exists to prevent.
* `brain.ops.egress.entities` is a second `Detector` beside the analyser's: it posts
  `pii.entity_request`, reads the answer with `pii.decode_entity_spans`, and an outage or an
  unreadable answer is a leg that adds nothing, so the rules' scrub stands and nothing is ever sent
  unscrubbed because the model was loading. `Detectors` asks the legs one after another within what
  is left of the time, passes over one that fails, and fails only when none answered; the first
  leg's spans are kept whole and the next only adds (`pii.merge_detections`).
* The entity model gets six seconds, not the analyser's two: it reads a window a second on a CPU,
  and two seconds would give it up on the first long passage and the leg would never be heard from.
  An install with only the analyser is exactly what it was.
* It is wired where the analyser is, when the process starts, and only for an install that runs
  the server (`INSTALL_SERVICES`) and chose the part (`INSTALL_MODEL_PARTS`), both set on purpose
  and neither true by default. A change reaches it at the next start, as the analyser's address does.
* An install check sends the part a sentence with a three-word name and holds that the name is gone
  once the scrub has run, waiting long enough for a cold load.

What was rejected

* Calling it from the sync gate (`gate.screening`): nothing outside tests calls that, and a network
  leg in a hot pure function is the wrong shape. The egress transport is the real caller.
* Reading the model's revision back, as the embedding leg does: nothing here writes a row, and a
  wrong-weights answer degrades one scrub, which the merge cannot turn into an unscrubbed one.

Not done, and a cost the owner should know: the first call after the part has been idle waits on a
model load longer than the leg's budget, so it is scrubbed by the rules alone; a longer idle time
keeps the part loaded. The checkpoint is fetched at whatever revision the hub serves and is not
pinned (needs-rupash 235). No check proves the scrub on a real install yet.
